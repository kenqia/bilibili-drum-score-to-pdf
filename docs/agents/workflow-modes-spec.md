# 三种模式实施范围

规格来自本次用户指令，基线提交 `079e51075d35c7ae9570bc9750c2cd77ba9466fc`。

公开 CLI 提供 `--mode auto|fast|full`。auto 和 fast 从 lazy 冷启动，启用最小证据链、干净原帧恢复及逐项脚本接受能力。full 保留既有 Agent-first 全量视觉路径。旧低层参数与既有任务保持兼容。只有新任务选模式，后续从任务继承，不能中途切换验证器。

冷启动的 review-plan 输出绑定当前观察 hash 的候选请求。candidate-plan 支持首次采样的几何建议，不要求已有 full 或 seed-proposal。所有建议均未确认，原生 clean、空间身份、标题、首尾及覆盖仍需实际审阅。脚本不调用视觉模型，也不把候选自动接受为事实。

auto 在必要时加强同一任务的原生视觉审阅，使用原帧和已有 ROI，不再次下载、导航或解码。不转换为旧 convert，也不降低 lazy 验证标准。fast 不自动加强整包审阅，达到既有预算后保留 waiting。full 模式仍可独立创建新任务；显式加强 fast 任务只扩充证据，不改变策略。

加强审阅最多执行一轮，最多读取 96 张原帧、生成其缺失的同帧原生 ROI；成本计入同一生命周期。明确内容冲突、来源篡改和无法解释的几何错配不能触发自动回退。新增证据没有自动呈交或视觉判断，必须重新绑定并审阅。

复用任务保存独立视频资产，核对原视频及副本 SHA256。原 full 目录移走后，新的任务仍能恢复、局部补采、导出和重放。复用只通过明确给出的可信任务匹配同一来源，不扫描私密目录、历史或认证信息。

软件验收边界已获用户确认，为公开 CLI 的模式选择、冷启动候选、受控加强审阅、旧目录移走后的恢复/导出/重放及保存的来源证据。最终运行完整 unittest，随后分别审查 Standards 与 Spec，提交当前分支。

auto 是目标日常默认，发布门槛包括上述软件验收与真实视频冷启动交付。在真实冷启动验收通过前，CLI 和 skill 默认保留 full，不把既有 full 复用成功或合成测试当作放行。完整宿主 Token、呈交及墙钟计量缺失时保留未知，不宣称性能达标。仅在显式需要时 replay。
